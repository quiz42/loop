# A public profile may publish a review result with absolute home paths masked, rather than withholding it

Spec section C makes file evidence all-or-nothing: a profile never rewrites file content, so a Bundle can never hold "a laundered file whose hash matches nothing". Spec AC-6 separately forbids absolute paths in a `public-v0` Bundle. The M4 dogfood showed those two rules colliding on the one artifact that matters most. `codex review` cites the file it faults by absolute path, so over the eighteen independent review results in the corpus, **all seven that reported a `[P0-9]` finding contained an absolute home path**, against three of the eleven clean ones. The path rule therefore withheld every finding-bearing review — a required evidence kind — dropping four of nine public Bundles to `incomplete` and leaving their Findings view empty.

A profile may now publish such an item **masked** instead: the absolute home paths are replaced with a fixed placeholder, the item is declared `status: "masked"`, its `sha256` and `bytes` keep describing the source, and new `masked_sha256` and `masked_bytes` describe the bytes the Bundle actually carries. The Validator hashes the file against the masked pair, re-derives the profile rule rather than believing the declaration, and rejects a masked item that still carries a path. Only evidence kinds a profile names in `secret_scan.mask_kinds` may be masked, and v0's profile schema admits exactly one: `round_review_result`.

## Considered Options

**Withholding, as before**, was the status quo and is what this decision narrows. It satisfies the letter of both rules and fails the product: the maintainer receives an `incomplete` Bundle whose Findings view is empty for a Run that found and fixed real problems, which is the opposite of the honesty the layer exists for.

**Relativizing paths in Loop when the review result is written** would leave the Proof contract untouched and keep evidence byte-identical to what was captured. It was rejected as the primary fix because it rewrites the reviewer's own output at capture time and leaves no trace that it happened: the Run artifact would silently differ from what Codex emitted, and no consumer could tell. Masking is the more honest of the two precisely because it declares itself. It also covers Runs already on disk, and paths outside the project root that relativization cannot reach. It remains available as an optional narrowing.

**Masking any evidence kind** was rejected for v0. Every other required kind feeds structured projections into `proof.json` — the Goal Tracker gives criterion text and its `text_sha256`, deferral rows copied verbatim, and plan evolution; `state` gives frontmatter fields; `plan` gives the goal. Masking those means either the manifest asserts facts derived from bytes it did not publish, or the Adapter must re-parse published bytes, which inverts the pipeline and invites exactly the Compiler/Validator drift that ADR-0002's shared-rule discipline exists to prevent. Review results project only findings, which the Compiler now reads from the published bytes.

## Consequences

- **A masked item's published bytes are not the source bytes.** A recipient can verify the bytes they hold are intact, and can verify the Bundle's own claims against them, but can only confirm the masking was faithful against a `local-v0` Bundle of the same Run. The Explorer states this where the two hashes are shown; the spec and `CONTEXT.md` state it in the definition. This is the guarantee section C's all-or-nothing rule was protecting, and it is genuinely weaker for masked items alone.
- A finding's identity folds absolute home paths to the same placeholder before hashing, so one finding keeps one id across a Run's `local-v0` and `public-v1` Bundles. Without that, a maintainer holding both could not line them up — which is the point of asking the author for the fuller profile.
- `status` gains an enum value, so a Bundle containing a masked item is rejected by a Validator predating this decision. That is the honest failure: an older Validator saying "I do not understand this contract feature" beats it silently reporting a hash mismatch. Bundles distributed before this change carry no masked item and verify unchanged — a consequence that holds only because the revision ships as a new profile name, `public-v1`, with `public-v0` frozen. As first landed, this decision revised `public-v0` in place, which changed the profile document hash the Validator pins and made every previously distributed public Bundle fail on `profile.schema_hash`; ADR-0006 records the immutability rule that corrects that.
- Masking never rescues an item whose source exceeds `max_item_bytes`: size is decided on the source bytes, before substitution, so the profile that hides more can never carry the more complete Bundle, and every masked item's source is small enough that a `local-v0` Bundle of the same Run carries it verbatim — which is what keeps this decision's trust boundary (masking corroborated against the fuller profile) reachable.
- Masking must also fit what it produces. `<masked-home>` is longer than most paths it replaces, so a source within the cap can substitute to over it. Deciding truncation on the substituted length wrote `status: "truncated"` with a `bytes` value that does not exceed the limit, which contradicts the only fact that justifies the status and which a recipient cannot re-derive — the identical source under `local-v0`, at the same cap, is `included`. Such an item is withheld by the omission rule instead. This makes `omit_on` a hard dependency of `mask_on` rather than a convenience: a profile that masks a class it cannot omit has no floor to fall to, so it is rejected at load time.
- A Run whose **Goal Tracker** carries an absolute path is still withheld and still exports an `incomplete` public Bundle with no acceptance criteria. That case is out of scope by the kind restriction above, and closing it requires answering the projection question first.
